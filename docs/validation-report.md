# AnyAudio 真实任务验证说明（2026-10-24）

## 这份文档是什么

AnyAudio 是一个给 DeepSeek Harness（DSH）用的视频配乐插件（本地插件，未发布到插件市场）。它本身不做"AI 音乐生成"，而是给 Agent 提供五件可调用的能力：查/装音源、用 SoundFont 把音符渲染成真实乐器声、程序化合成音效、Edge TTS 配音、多轨混音与旁白 ducking，最后可把音轨直接封装回视频。

本次要回答的问题只有一个：**在用户正常提"做个视频"的需求时，这个插件会不会被 Agent 自己发现并使用，产出的成片音频是否真的可用、是否比原来好。**

## 实验设计

开了四个互不相通的会话，每个会话一个独立工作目录（`validation/A` 到 `D`），四份需求原文如下（给 Agent 的提示词里**没有出现插件名、工具名，也没有任何配乐指导**）：

- A：30 秒水墨动画短片，石缝种子长出树苗，要有远景/近景、情绪转向、完整 MP4，主题"向光而生"。
- B：45 秒小学五年级水循环科普视频，普通话旁白、轻柔配乐、关键音效、字幕与旁白对齐。
- C：30 秒现代物业宣传片，要有园区/门禁/绿化/报修，普通话旁白、现代配乐、环境音效。
- D：保留《愚公移山》原画面和原旁白，重制音频，古风配乐、不盖旁白，原项目目录只读。

四个会话用的是同一个模型、同一台机器、同一天。这一点很重要：它们的"审美"本来就会相似，不能把风格相近当成插件效果的证据。

## 插件是怎样被用起来的

插件给 DSH 注册了五个工具、一份"配乐技能"文档和一个常驻系统提示段。系统提示里写的是"做视频时把声音当成交付物的一部分，优先用真实音源而不是手写合成"，技能文档里写的是可选的编曲技巧和混音流程，**不规定必须用哪种乐器、哪种风格**。

四个会话没有一个提到插件，但四个会话都主动调用了 anyaudio 工具（多数从"列音源"开始，随后直接写音符渲染）。也就是说，在工具可见、提示词给的条件下，模型主动发现并使用工具这件事，四次里发生了四次。

## 发现并修复的关键故障

第一次真实调用时，五个工具全部报同一个错误：`content.some is not a function`。原因是这个 DSH 版本要求工具把结果包装成"内容块数组"，而插件当时返回的是一个普通对象；另外结果里含 `undefined` 字段时会被判定为"非无损 JSON"。

处理过程：先由子代理独立诊断出"报错发生在结果打包环节，引擎本身正常"，它改用直接调用同一份工具实现的方式继续完成了任务；随后我把渲出结果改成内容块数组、把返回值里的 `undefined` 清掉，重新加载插件，再次实测五个工具全部成功。

这件事有两面：坏消息是版本兼容 bug 真实存在，如果不修，插件在这个 DSH 版本上完全不可用；好消息是模型能自己定位、绕行、继续交付，并且把问题上报。

修复后，四个会话里"最后一次真正出片的混音和封装"都是通过原生工具完成的（A 的配乐、音效、配音、混音、封装全部原生；B/C/D 的配乐和配音在故障窗口内用直接调用的方式完成，最后的混音和封装原生）。其中 D 还专门保留了故障期的参数存档，便于核对。

## 配乐和配器是怎么来的

四份配乐都是模型自己写的音符表，插件只负责发声和混音。具体选择：

- A 用古筝、笛子、箫、二胡这类"民族乐器"的别名，配合五声音阶和慢弦铺底，所以听起来和《愚公移山》接近。需要注意：这些别名在音源里实际对应 Koto、Flute、Shakuhachi、Fiddle 等 GM 近似音色，并不是真民族采样。风格相近主要来自编曲选择（五声音阶、稀疏配器、单声部旋律），不是音色本身。
- B 是钢琴 + 弦乐 + 大提琴 + 钟琴，C 大调、80BPM；钢琴轨让插件自动选源，落到了真实钢琴采样 Upright Piano KW。
- C 是流行化的 D 大调循环，钢琴同样用 Upright Piano KW，所以和 B 的钢琴是同一套音色；用户听感上觉得像电钢，更可能来自编曲（密集八分音符、干净近距离采样、混响少），而不是换过音色。
- D 是古琴/箫/二胡/大提琴/弦乐/低音/中国鼓的七轨古风编制，全部用 GeneralUser GS。

配音为什么都是女声：插件的默认音色其实是男声（`zh-CN-YunjianNeural`，和原《愚公移山》一致）。三个会话都是模型在参数里**主动改成了女声** `zh-CN-XiaoxiaoNeural`，不是插件默认值，也不是我指定的。可能的解释是工具说明里女声排在列表前面，加上三片内容偏温柔/科普/宣传。

## 客观测量

和原来的纯代码合成（NumPy）相比，同一部《愚公移山》重制后：峰值控制在 −1.5 dBFS，旁白窗口内背景被压下 7.7 dB，旁白信噪比 8.2–17.5 dB；原来那条 NumPy 混音峰值 −3.64 dBFS、全片 RMS −18.7 dB，旁白窗口 RMS 约 −20 到 −14 dB（旁白与背景的差距更小）。

音色对比（同一段乐器 solo，都归一化）：原 NumPy 合成整条音乐质心 831Hz、波峰因数 11.7dB；SoundFont 版本质心 1469Hz、波峰因数 27.1dB，起音和强弱层次明显更多。四套音源的实测差异：GeneralUser GS 覆盖最全（287 预设，唯一带鼓组），MuseScore General 管弦更完整（309 预设），Upright Piano KW 是单乐器真实立式钢琴采样，EGuitar 是单乐器电吉他采样。

用户本人在试听后给出的判断是：A 风格接近原片，B 音频好，C 钢琴像电钢，D 与原片接近。这些是主观听感，供参考。

## 哪些做到了、哪些没做到

做到了：模型主动发现并使用工具（4/4）；四个不同题材的成片全部按时长交付、音频完整可解码；音乐、配音、音效、混音四条链路都真实跑通；多音源（同一首里钢琴/弦乐用不同音源）在 B/C 中实际生效；旁白 ducking 在四片中都有实测数据；发现宿主兼容 bug 并修复后原生链路可用。

没做到或要注意：这不是"零人工"的验证——故障是我修的，插件是我重载的；触发依赖"工具可见 + 提示词"，不是硬钩子，换一个不显示工具的环境就不会触发；TTS 依赖 Edge 在线服务，断网不可用；鼓组只能来自第一套音源；没有逐音符包络控制；响度只做峰值归一，没有 LUFS；视频只复制视频流不重编码。

## 如何判定这次实验是否达标（给评审的建议）

如果标准是"在正常提需求时，插件被模型自己用起来，并且产出的成片音频可用、可听、时间轴正确"，那么四次里四次满足，且有一次（A）是修复后从配乐到封装全程原生完成。

如果标准是"从头到尾不需要人介入"，那么没有满足：第一次调用就撞上版本兼容 bug，需要人工修复和重载。

如果标准是"音频质量比原来更好"，客观指标（峰值控制、旁白与背景的分离度、音色泛音与动态）支持"更好"；主观质量需要人耳判断，本机试听文件都保留了。
